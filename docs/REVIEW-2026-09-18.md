## Verdict in three sentences

No, not as planned: I would build the validation stage and the retro loop in a different order and with a different shape, and I would not build the cost-per-accepted-milestone scorer at all in its proposed form. The single biggest risk is that the plan's "script decides" principle is nominal in exactly the two new parts: in validation the same model writes the claims, the kill numbers, the source list and the interpretation, so the referee only checks that the model agreed with itself; in the retro loop the rdx-eval scorer's code and corpus live inside the worktree the executor edits, so "an executor cannot edit its own judge" is already false on this repo. Fix those two before adding anything.

## Gaps

1. **No test of the one thing validation depends on: fetching evidence from a headless child.** CHANGELOG v3.1 records that the inspiration stage "had no web access"; `agents/reviewer.md` and `agents/exec-*.md` disallow `WebFetch`/`WebSearch`; `loop/allowlist.py` has no rule for either. The plan's step 3 "one real validation run with real fetching" is the first time this is checked. Add a step 0: a $0.50 `claude -p` child that fetches one URL and one JSON API through `pipeline/child.sh` and writes a ledger row. If that fails in the cloud, the stage only runs on the Mac, which changes the build order.

2. **Nothing separates the model that writes kill numbers from the model that chooses sources.** One model does claims, kill numbers, sources, and interpretation. A model that wants a GO will write `kill_value` it expects to clear. The referee checks internal consistency only. Add a second fresh context that sees `claims.json` and writes `plan.json` (measure, source, kill number) without seeing the original model's reasoning, and have the skeptic propose its own kill numbers per claim; the referee flags any claim where the author's kill number is laxer than the skeptic's.

3. **No conviction-tier → build-cost table, so the referee cannot compute "the reported conviction tier is the one the ledger supports".** Deferred to open questions. Without it the verdict is uncomputable by script and the stage degrades to model judgment plus a human read. Write the table now, even provisionally (build_usd < 20 → tier 1 on one claim; < 100 → tier 2 on every claim; ≥ 100 → tier 3 on the core claim), and make the referee's exit code depend on it.

4. **No claim is marked as the core assumption.** CLAUDE.md "Feasibility First" and `commands/jg-feasibility.md` both require identifying *the single core assumption*. `claims.json` has 3–6 peer claims. A GO with five soft claims green and the core claim "unobtainable" must be NO-GO or needs-human; the referee cannot enforce that without a `core: true` flag. Rule: core claim below the required tier → exit 3 regardless of the others.

5. **No handling of source drift or paid sources.** "Re-runnable source" is checked by presence, not by re-running. A URL that 404s a week later, or an API needing a key, silently becomes tier-0 evidence with a tier-2 label. Have the referee actually re-fetch `cmd`-kind sources (fake fetcher in tests, real in the run) and store the response hash in the ledger.

6. **The retro's facts have no schema and half have no data yet.** `retro/facts.json` wants first-try acceptance rate, nights ended flat, gate false fires, human overrides, time to green. Today pocket-notes' `.pipeline/build/state.json` stores only `status` and `note` per milestone (no attempt list); no record of human overrides exists anywhere; "gate false fires" is only measurable against a labelled corpus that `rdx mine` writes to a gitignored file. Write the facts schema first and instrument the drivers (`pipeline/build.sh` emits `attempts` per milestone; ship and merge gates log `human_override`). Otherwise the collector is a model-shaped script reading prose.

7. **`spec.json` has no `human_gates` enforcement, and the plan adds a seventh gate.** `pipeline/spec_check.py` never reads `human_gates`. Nothing stops `/jg-spec` from running on an idea that was never validated or was NO-GO. Add: `spec_check` exits 3 when `.pipeline/validate/<slug>/verdict.json` is absent or NO-GO without `overruled`, unless `--no-validate` is passed and logged.

8. **Retro proposals have no path into the picker.** `loop/pick.py` special-cases only `source: planner`; `loop/backlog_io.py` does not validate `source` at all. `source: retro` rows get picked at rung 1 like any other. Decide whether retro rows are rung 2 (cooling-off like planner rows), and what `dimension` "human overrides" or "nights ended flat" map to — none of the existing scorers. The README's one rule ("a row without a scoreboard dimension is not a candidate") makes most retro rows unpickable.

## Weak assumptions

- "Pocket Notes 97.8→97.9" as proof Nightshift works on pipeline projects. The project's `.loop/scores.jsonl` says iteration 1 had `outcome: reset-flat` (delta +0.147, below `FLAT_EPS` 0.5). The driver threw that iteration away. The evidence supports "the loop ran and did nothing harmful", not "it improved the product".

- "cost meter agrees with the bill within 5%". Pocket-notes only. This repo's `.loop/events.log` shows live/result disagreement of 8%, 21.5% and 32% across three runs, one with `DRYRUN ... ok=false`. The dryrun tolerance in `loop/README.md` is [−10%, +35%], not 5%.

- "ARD finds evidence sources the model cannot reach with a browser (a chain explorer, an exchange API, a registry)". I ran `rdx search "fetch ethereum on-chain transaction volume from a block explorer api"`: top hits `openapi-fetch`, `chaingate`, `solhint`; decision `silent reason=no_intent`. ARD indexes MCP servers, plugins and npm packages, not data sources. It will not find Etherscan. Drop this role or build a data-API funnel, which is a project in itself.

- "gate precision 1.0 / recall 0.75 on a 124-case labelled corpus". `rdx eval` today: 21 true positives, 7 false negatives, 95 true negatives. Precision 1.0 is over 21 fires. Fine for the gate; thin as a Nightshift scorer dimension with `target: 100`, because the only headroom (recall 0.75) is 7 cases and the corpus file is editable from the worktree.

- "Nightshift runs on this repo against its scorers: the three test suites". The repo's actual config has one tests scorer, `cd discovery && pytest`, and `main_branch: claude/agentic-resource-discovery-xe20jh` (the current branch, not `main`). `loop/tests` and `pipeline/tests` (296 tests, all pass) are not scored. GOAL.md line 4 has no scorer behind it.

- The tier ladder: tiers 4 and 5 require a product to exist; for a *pre-build* validation they are unreachable by construction, and tier 3 needs the human to interview people, which the plan lists as open. In practice the ladder is 0–2, all model-fetched. Say so, or "conviction tier scales with cost" will demand tiers the stage cannot produce.

- "Measure with the retro's cost-per-accepted-milestone scorer". A scorer per `loop/README.md` "Scorer contract" prints one JSON line, runs in seconds, needs 3 baseline runs to derive `eps`, and is pinned by the manifest. Cost per accepted milestone requires a real build on a real project with real spend ($3–5 per milestone, 20+ minutes). It cannot satisfy the contract, and its variance across projects will exceed any usable `eps`. It is a report metric, not a scorer.

## Contradictions

1. **Three feasibility mechanisms, no retirement plan.** `commands/jg-feasibility.md`, `pipeline/prompts/interview.md` Round 4, and the proposed `/jg-validate`. `DEAD_ENDS.md` says every extra `/jg-*` command "dilutes muscle memory". The plan must say `/jg-validate` replaces `/jg-feasibility` and Round 4 becomes "read verdict.json", or the human will run the cheap one and skip the expensive one.

2. **`commands/jg-skeptic.md` vs `agents/skeptic.md`.** Same name, different contracts. One will shadow the other.

3. **`DEAD_ENDS.md` "Custom subagent configurations in the kit — ruled out"** vs `agents/` with eight definitions and the plan adding two. Annotate the dead end as superseded with the reason.

4. **"Scorers live outside the worktree so an executor cannot edit its own judge"** vs this repo's `rdx-eval` scorer: `discovery/rdx/loopscore.py`, `evalharness.py`, `retrieve.py` thresholds and `discovery/corpora/gate.starter.yaml` are all inside the worktree; the manifest pins only `config.json`, `scorers/cmd.py`, `scorers/tests.py`. `loop/check_plan.py` only forbids `.claude/`, `.loop/`, `.git/`. An executor can raise recall to 1.0 by relabelling seven cases. The reviewer is the only defence, and it is a model.

5. **Exit codes.** Plan: `3 pivot / needs-human`. Pipeline contract: `3 needs-human`. PIVOT is a verdict, not a stall.

6. **Privacy.** The retro is fed from transcripts; `discovery/rdx/mine.py` says mined prompts "must never be committed". A fact from a transcript must be a count, never a quote; the plan does not say so.

7. **Principle 2 "the judge never saw the pitch"** vs the evidence judge that "reads only plan + ledger". `plan.json` is the pitch in structured form.

## The validation stage specifically

- **Self-consistency is not correctness.** The failure mode is not a model that contradicts itself; it is a model that writes `kill_value: 100 monthly downloads` for a claim that should need 10,000. The skeptic is the only counterweight and its output is prose with no numeric hook the referee can use.
- **"Plan frozen before evidence" is checked by timestamps and a sha the model produces.** Freeze must be enforced by the driver: the driver writes `plan.json`'s sha and `frozen_at`, then starts a *new* child for fetching with read-only access to plan.json.
- **Sources are chosen by the party being judged.** Selection bias is the dominant error in idea validation and nothing addresses it. Minimum: the skeptic names two disconfirming sources per claim before freeze, and the ledger must contain a row for each (possibly "unobtainable").
- **The judge's second question, "does the case against outweigh the case for", is the verdict.** Keep the judge on question one only (does the cited source really describe the pain, 0/1/2 per ledger row with a quoted line) and let the script compute the verdict from tiers and kill numbers.
- **Tier ladder.** Sound as an ordering; unsound as a scale. Collapse to four: 0 none/unobtainable · 1 anecdotal · 2 primary data (query + result + date, re-runnable) · 3 observed use. Require *n* independent tier-1 sources to count as one tier-1 point, not one link.
- **Overrule policy.** The overrule should be stored as a claim with a `kill_value` and re-checked by `/jg-feedback` so a wrong overrule becomes a measured fact for the retro.

## The self-improvement loop specifically

- **It will optimise the numbers it can move.** On this repo it already did: three iterations, tests 80.7→97.0 (coverage), `rdx-eval` 91.68 unchanged. The only rdx-eval headroom is gate recall (7 cases), and the cheapest way to move it is inside the worktree. Pin `discovery/rdx/loopscore.py`, `evalharness.py` and every corpus file in the manifest, or move the corpus and scorer out of the repo like `config.json`.
- **Retro proposals have no dimension**, so `pick.py` cannot select them.
- **The cost-per-accepted-milestone scorer cannot be a scorer.**
- **Kit changes break every project's manifest.** A retro iteration that edits `loop/scorers/tests.py` invalidates every project until re-signed by hand. The loop will not know it did that.

What would make it improve the system rather than its scores: a `kit-eval` scorer that runs the fixture suites end to end plus a frozen replay of real stream logs through `tail.py` asserting cost agreement; the retro produces a *report and a corpus* (each fact becomes a labelled regression case, the scorer is the pass rate on that corpus); cost per accepted milestone goes in `report.py` as a trend, never as a keep/undo input.
