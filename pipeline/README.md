# The project pipeline — contract

Idea to Nightshift: six commands on one spine. This file is the contract every
script, prompt and agent in `pipeline/` is built against. Nightshift
(`loop/`) is stage 7 and is reused, not duplicated: the same agents,
worktrees, guards, allowlist, `check_plan.py`, `merge.sh` and scorers.

Principles carried over from Nightshift, non-negotiable:

1. **A script decides, never a model.** Done, kept, merged, shippable: each is
   a program's exit code.
2. **Every stage writes a file; the next stage reads it with fresh context.**
3. **Nothing installs itself. Nothing touches `main`.** Human gates are
   explicit and listed below.
4. **If it can't be measured it becomes a question for the human**, never a
   guess.
5. **Cheapest model that can do the job.** Fable plans, interviews and
   reviews; Sonnet executes and plays the persona; Opus only for `hard`;
   Haiku for chores.

## spec.json (the spine)

```json
{
  "version": 1,
  "name": "Pocket Notes",
  "one_liner": "A single-page notes app that works offline.",
  "stack": {"language": "javascript", "runtime": "node", "ui": true, "llm": false,
            "data": "localStorage", "serve": {"cmd": "npm run dev", "port": 5173},
            "deploy": {"kind": "static", "cmd": "npm run build"}},
  "needs": ["ui", "unit-tests", "coverage", "lighthouse", "persona", "perf"],
  "milestones": [
    {"id": "m1", "title": "Create and list notes", "depends_on": []},
    {"id": "m2", "title": "Search and edit",       "depends_on": ["m1"]}
  ],
  "features": [
    {"id": "f-001", "milestone": "m1", "title": "Create a note",
     "description": "A 'New note' button opens an editor; saving adds it to the list.",
     "acceptance": [
       {"type": "test", "cmd": "npm test -- notes.create", "must": "pass"},
       {"type": "persona", "task": "Create a note titled 'groceries' and see it in the list",
        "max_steps": 4, "must": "complete"},
       {"type": "lighthouse", "url": "/", "min": {"accessibility": 90, "performance": 80}}
     ],
     "priority": 1},
    {"id": "f-002", "milestone": "m2", "title": "Search notes",
     "acceptance": [
       {"type": "test", "cmd": "npm test -- notes.search", "must": "pass"},
       {"type": "perf", "cmd": "node bench/search.js", "metric": "ms_p95", "max": 50},
       {"type": "manual", "what": "Search feels instant on 1,000 notes"}
     ],
     "priority": 2}
  ],
  "success": [
    "Every feature's acceptance passes",
    "Coverage of src/ >= 85%",
    "A new user completes every persona task within its max_steps"
  ],
  "budget": {"build_usd": 40, "nightshift_cap_usd": 25},
  "human_gates": ["spec", "installs", "milestone-merge", "tokens", "deploy"]
}
```

Rules `spec_check.py` enforces (exit 2 on any violation, one line per problem):

- every feature has ≥ 1 acceptance entry; at most one may be `manual`; a
  feature whose only entry is `manual` is listed in the summary as
  "unmeasurable" and counted — the spec is still valid but the count is printed
  and must be ≤ 20% of features;
- acceptance types and required fields:
  `test {cmd, must:pass}` · `perf {cmd, metric, max|min}` ·
  `lighthouse {url, min:{category:score}}` · `persona {task, max_steps, must:complete, setup?:[driver actions]}`
  (every walkthrough starts in a fresh browser; `setup` is the scripted state the
  task starts from — replayed before every persona action, never counted as steps) ·
  `gate {name, kind:screenshot|perf, ...}` · `evals {cmd, min}` · `manual {what}`;
- milestone ids unique, `depends_on` acyclic, every feature's milestone exists;
- `needs` ⊆ {ui, unit-tests, coverage, lighthouse, persona, perf, evals, llm, db, auth, deploy}, and
  must include every scorer an acceptance check implies (test→unit-tests, persona, lighthouse, perf, evals);
- `stack.serve {cmd, port}` is required when any persona or lighthouse check exists;
- `success` lines ≥ 1, each ≤ 120 chars, numbered in GOAL.md in order.

`spec_check.py --derive` (idempotent) writes:

- `GOAL.md`: the `success` lines numbered, then one line per feature
  `F. <id> — <title>` so reviewers can cite either.
- `.loop/backlog.yaml` rows appended (never duplicated by id) for each feature:
  `id: spec-<feature id>`, `title`, `dimension` = the feature's first
  measurable acceptance type mapped to a scorer (`test|coverage→tests`,
  `perf→perf`, `lighthouse→lighthouse`, `persona→persona`, `evals→evals`),
  `source: spec`, `rung: 1`, `status: open`, `note: milestone <id>`.
- `.pipeline/acceptance-index.json`: `{feature id: {milestone, checks}}` for gates.py run-all and ship_check.
- `.gitignore` additions for the pipeline's scratch directories.
- `SPEC.md` if absent (a readable rendering; never overwritten once it exists).

## Stage 0 — /jg-validate (is it worth building?)

`bash pipeline/validate.sh --project . --idea "<idea or URL>" --build-usd N`.
Runs before the interview and replaces `/jg-feasibility`. Eight roles,
each a fresh `claude -p` child through `child.sh`, each writing a file the
next reads; the script between them does the redaction, the freeze, the
budget and the verdict. A model judges what to measure and what it means; a
script holds it to the numbers it wrote before looking.

| role | model | reads | writes |
|---|---|---|---|
| author | fable | the idea (and the last ledger on a PIVOT) | `claims.json`: 3–6 claims, one `core`, no numbers |
| setter | fable, fresh | claims, budget, reachable hosts | `plan.json`: measures (name, unit, direction, kill_value, sources) |
| skeptic | fable, fresh | claims, `plan.redacted.json` (numbers removed by the driver) | `skeptic.json`: its own kill numbers, added measures, two disconfirming sources per claim; `skeptic.md` |
| freeze | script | plan + skeptic | `plan.frozen.json`: the stricter number per measure, added measures, required sources; `freeze.sha` |
| fetcher | sonnet, fresh | the frozen plan (read-only; the sha is checked after) | `ledger.jsonl` via `fetch.py` only; `bodies/` |
| judge | sonnet, files only | plan, ledger, bodies | `judge.json`: 0/1/2 per row with the quoted line |
| referee | script | everything above, `reachable.json` | `verdict.json`, `VERDICT.md`; `DEAD_ENDS.md` on NO-GO |
| human | | `VERDICT.md` | an overrule, in writing, stored with the verdict |

Under a $20 build budget only author, setter, fetcher and referee run.

Tiers per ledger row: 3 an experiment's number (`--source-kind
experiment`) · 2 a re-runnable number (`json:`/`regex:`/`count:`) whose
value survives the referee's re-fetch (drift = absent, or moved across the
kill number) · 1 a `text` row the judge scored ≥ 1; three rows with
distinct origins make one point; the skeptic's required sources never
count as support · 0 a failed fetch, a judge 0, a free-text origin.

Required per band (`validate.toml`, `--build-usd`): small (< $20) core at
tier 2; mid ($20–100) core at tier 2, others at tier 1; large (> $100) all
at tier 2 plus one tier-3 row before any milestone with dependencies,
which `milestone.py next` enforces (exit 3).

Verdict: core killed or below tier → NO-GO (2); a non-core claim killed or
below → PIVOT (5; the driver re-runs the author once with the ledger, a
second PIVOT is NO-GO); a required source blocked here per `reachable.json`
→ infra (4, run it where the host answers); unmatched measure at freeze or
cap reached → needs-human (3); else GO (0). The stage total (`validate.toml
budget.usd`, $12; $4.50 on the small band) is the sum of this slug's ledger
rows across PIVOT passes; a PIVOT pass keeps the ledger and re-fetches only
what the revised claims need. Measured on the first real run (2026-09-18,
a $15 idea in the cloud): author $0.87, setter $0.69, fetcher $0.33, the
verdict PIVOT on two supporting claims killed by registry numbers; the $2
cap of the plan could not afford the re-run, hence $4.50.

Files under `.pipeline/validate/<slug>/` (slug = sha256(idea)[:8]); `bodies/`
is gitignored, the rest is committed. GO hands off with `validate.py
handoff`: the claims become `spec.anchors`, the kill numbers success lines,
and `spec.validation {slug, verdict_sha256, validated_budget_usd}` is what
`spec_check.py --gate-validate` reads (missing or NO-GO verdict → 3; build
budget above the validated one → 2; specs without the block are reported,
not failed; `validation: {skipped: true, by}` is allowed and named).

## Stage 1 — /jg-spec (interview)

Interactive; Fable with the human present. `prompts/interview.md` runs 3–4
rounds through the terminal question prompt. Every round ends by rewriting
`spec.json` and running `spec_check.py`. The rounds:

1. What is it, for whom, one-liner, stack guess (assess.py if a repo exists).
2. Features → milestones with dependencies; priorities.
3. For each feature, the checks: the prompt offers the type menu and refuses
   adjectives ("fast" → "perf, which command, which number").
4. Success lines, budget, deploy target. Feasibility: the CLAUDE.md rule; a
   no-go is written to DEAD_ENDS.md and the command stops.

Unattended mode for tests: `--answers <file.json>` supplies the human's
answers per round; the same prompt is run as `claude -p`.

Human gate: **the human says "signed"**; the command then commits
`spec.json`, `SPEC.md`, `GOAL.md` with message `spec: v1 signed`.

## Stage 2 — /jg-tools

`tools_plan.py --spec spec.json --assess <assess.json>` → `.pipeline/tooling-plan.json`:

```json
{"gaps": [{"need": "coverage", "why": "spec needs coverage; assess: no coverage tool for vitest",
           "candidates": [{"slug": "@vitest/coverage-v8", "kind": "npm-dev", "version": "4.1.11",
                           "source": "rdx|web|known", "tier": "green"}],
           "chosen": null}],
 "ready": ["ui", "unit-tests"], "unresolved": []}
```

Sources, in order: a fixed table of known dev tools per need+stack (`KNOWN`),
then `rdx search "<need> <stack>"` (Claude ecosystem), then the planner may
add web-found candidates by hand into the plan file. `--verify` re-runs
assess.py and marks each gap `closed` or `open`; exit 3 if any gap that a
`needs` entry requires is still open. Installs are done by the existing rdx
install runner (human-gated) or by the human; the script never installs.

Human gate: **every install**.

## Stage 3 — /jg-build

`milestone.py --spec spec.json --state .pipeline/build/state.json next` prints
the next milestone whose dependencies are all `done`, or `none`. Per milestone
the planner (`prompts/build.md`, run interactively or as `claude -p` in tests)
does what Nightshift's iterate.md does, with these differences:

- target = all features of the milestone; `plan.json` subtasks reference
  feature ids in `row` (e.g. `"row": "f-001"`); `check_plan.py` accepts ids
  from `target.task_ids` as before;
- executors work in worktrees under the same guard; reviewers cite a GOAL.md
  line (success or feature line);
- merges go to ONE build branch `build/<date>` (worktree `.pipeline/wt/build`)
  via `merge.sh`; an accepted milestone is tagged `build/<milestone>`;
  `NIGHTSHIFT_CONFIG` = the project's Nightshift config, written by
  `mkconfig.py` from the spec when `/jg-loop init` has not run;
- after merging, `accept.py --spec spec.json --milestone m1 --workdir <wt>`
  runs every acceptance check of the milestone's features and writes
  `acceptance.json` `{milestone, features: {id: {checks: [{type, ok, detail}], ok}}, ok}`;
  exit 0 all ok · 2 some failed · 4 infra (a check could not run).
  Persona checks are run through `ux_score.py` (below); lighthouse through the
  existing scorer; `gate` through `gates.py`.
- a milestone is `done` only on accept exit 0; on 2 the planner gets one
  more iteration on the failed features, then the milestone is `blocked` with
  the failures in `summary.md` and a needs-human row.

Human gate: **`git merge --no-ff build/<date>` (or the milestone tag) into main**, printed, never run.

Costs: the planner appends to `.pipeline/ledger.jsonl` after each milestone
(`claude -p` children are metered by tail.py exactly as in Nightshift; an
interactive session records the session's own cost as reported by /cost).

## Stage 4 — /jg-ux

**Persona.** `agents/persona.md` (Sonnet; tools Bash, Read, Write; no Edit;
writes only under `.pipeline/ux/<run-id>/`). Input: `{url, task, persona,
max_steps, run_dir}`. It drives the page with `js/persona_driver.cjs`, which
takes a small JSON "script" of actions the agent decides one at a time
(`goto`, `click <selector|text>`, `fill`, `press`, `read`) and appends every
action, the visible text after it, and a screenshot path to `trail.json`.
The agent stops when the task is done, when it is stuck (3 actions with no
progress), or at `max_steps × 2`. Final message: JSON
`{"status":"complete|stuck|error","steps":N,"dead_ends":[...],"confusions":[...],"trail":"<path>"}`.

`ux_score.py --run <run_dir> --check '<persona acceptance json>'`:

- counts: `completed` (status complete and steps ≤ max_steps ×1.5),
  `step_ratio` = max_steps / steps (capped at 1);
- judgment: spawns nothing itself; it reads `judge.json` if present. The
  planner invokes `agents/persona-judge.md` (fresh context, read-only) with the
  trail and the fixed rubric in `prompts/rubric.md` (5 criteria, 0–2 each:
  findability, feedback, recovery, consistency, wording), which writes
  `judge.json` `{"scores": {...}, "total": 0-10, "evidence": [...]}`;
- `score.json`: `value = 100 × (0.5·completed + 0.3·step_ratio + 0.2·judge/10)`;
  without judge.json the judge share is redistributed and `judged: false`;
- non-numeric findings (`confusions`, `dead_ends`) become backlog rows
  `dimension: persona, source: persona` via backlog_io, deduplicated by title;
  a later walkthrough of the same task that completes with no findings marks
  that task's open `ux-*` rows done (`note: … superseded: clean walkthrough
  <run>`), so a stale finding cannot cost Nightshift a night.

`loop/scorers/persona.py` (Nightshift scorer): config `{name: persona,
serve_cmd, port, tasks: [{task, max_steps, persona}], runs}`; starts the
server, runs each task through `claude -p --agents` with the persona agent,
scores with ux_score, value = mean. `ok:false` when the server or the agent
cannot run. This is what lets Nightshift move "how it feels".

**Tokens.** `tokens_extract.py --url <u> --out .pipeline/ux/design-tokens.proposed.json`
uses Playwright to read computed styles of the body, headings, buttons, inputs
and links: font families, a type scale (distinct font sizes, sorted), spacing
scale (distinct margins/paddings/gaps, sorted), colors (distinct, by
frequency, top 12), radii, shadows. Output is a proposal; the human approves
by copying it to `design-tokens.json` (the command offers to do the copy).

**Inspiration.** `prompts/ux.md` step: the planner searches curated sources
(a list in the prompt) for five references matching the spec's UI
description, screenshots each with `js/snap.cjs`, and writes
`.pipeline/ux/inspiration.md` with "what to take" per reference. Inspiration
only; assets are never copied.

Human gates: **tokens approval**; **design direction**.

## Stage 5 — Tests

Gates (`gates.py`, pass/fail, run by `accept.py` for `gate` checks and by
`merge.sh` when `NIGHTSHIFT_GATES_CMD` is set):

- `screenshot`: `{name, url, viewport:[w,h], theme:light|dark, threshold:0.01}`;
  `js/snap.cjs` renders with animations disabled, fixed viewport, fonts
  loaded; compared pixel-wise to `.pipeline/gates/baseline/<name>.png` (a
  pure-Python PNG diff, no extra dependency); missing baseline → exit 3
  `needs-baseline` (the human approves by `gates.py --accept <name>`);
- `perf`: `{name, cmd, metric, max|min}`; the command prints one JSON line;
  the metric is compared to the budget.

Evaluations are scorers: tests (with coverage), perf, lighthouse, persona,
evals. `spec_check --derive` writes the Nightshift scorer list into
`.pipeline/scorers.proposed.json` from `needs`; `init.py` reads it when
present.

Human gate: **first baseline approval**.

## Stage 6 — /jg-ship

`ship_check.py --spec spec.json --workdir . [--tag vX]` → `.pipeline/ship/<tag>/ship-report.json`
with one row per check, `ok` overall, exit 0/2/4:

1. `accept.py` for every milestone passes;
2. `git status` clean, on `main`, CHANGELOG.md has an entry for the tag;
3. `.env.example` keys ⊇ keys referenced in code (`process.env.X`, `os.environ["X"]`, `os.getenv("X")`);
4. secrets scan: no strings matching common key patterns outside `.env`;
5. lighthouse minimums from the spec on a served build (skipped with reason
   when `needs` lacks lighthouse);
6. security review: the human ran `/security-review` this session (the
   command asks; recorded as a `manual` row);
7. gates pass.

Then the planner (`prompts/ship.md`) prints the deploy command from
`spec.stack.deploy.cmd`, waits for the human, runs it, runs one persona smoke
task against the live URL, tags `release/<tag>`.

Human gate: **the deploy**.

## Fetching evidence: `fetch.py`

The validation stage's only way to touch the network is a script,
`pipeline/fetch.py`, never `WebFetch`: a ledger row must carry something the
referee can re-run. `fetch.py get <url> --extract json:<path>|regex:<re>|count:<re>|text
[--run-dir D] [--ledger L --claim C --measure M --origin HOST]` writes the
body (HTML stripped, capped) to `<run-dir>/bodies/<sha256>.txt`, prints one
JSON line with `value`, `extracted_by`, `body_hash`, `date` and a `reason`
(`egress | 404 | paywall | timeout | http | extract`) on failure, and
appends the ledger row. `--origin` must be a host or a handle, never free
text. `fetch.py probe --out reachable.json` fetches a fixed host list and
records which hosts answer 2xx from here.

Smoke-tested headless on 2026-09-18: a `claude -p` Sonnet child through
`child.sh` ran the probe and two fetches for $0.08 with no denies. From a
cloud session the reachable set is registries (npm, PyPI, crates.io) and
raw GitHub files; api.github.com, Reddit, Hacker News, Product Hunt, Stack
Overflow, dev.to, Wikipedia, arXiv, search engines and chain explorers are
refused by the proxy. The referee reads `reachable.json` to tell "blocked
here" (infra, run it on the Mac) from "nobody has it" (unobtainable).

## Stage 7 — Nightshift

Unchanged in the loop; the handoff is three facts:

- the config is the one `/jg-build` wrote with `mkconfig.py` (perf checks
  become the perf scorer's `bench_cmd` + `baseline`, persona checks its
  tasks with their `setup`); re-run `mkconfig.py` after the spec changes,
  it re-signs the manifest;
- `run.sh` finds no `scores.jsonl` (the project never ran `/jg-loop init`)
  and scores the baseline itself as iter 0 before the first iteration;
- the backlog already holds the spec rows, the persona rows from every
  walkthrough (`ux-*`) and the inbox rows (`fb-*`), so `pick.py` has a
  measured target from the first night.

`bash loop/run.sh --dryrun --cap 8 --project <dir>` is the proving run.

## Stage 8 — /jg-feedback

`feedback.py --inbox FEEDBACK.md [--sentry export.json] --backlog .loop/backlog.yaml`:
each top-level bullet in the inbox under a `## <date>` heading becomes a row
`source: production, rung: 1, dimension` from keyword mapping (crash/error →
tests, slow → perf, confusing/can't find → persona, else none → needs-human),
`title` = the bullet, deduplicated by normalized title; processed bullets are
moved under `## processed <date>`. Exit 0; prints the rows added.

## Human gates, in one list

the validation verdict · spec signed · every install · milestone merge to
main · tokens approval · first screenshot baselines · deploy. Each is
enforced by a script that refuses without the gate's artifact.

## Test plan

- pytest per script (`pipeline/tests/`), fixtures under `pipeline/tests/fixtures/`.
- `pipeline/tests/test_pipeline.sh`: a synthetic project run through
  spec_check → derive → milestone → accept (with fake commands) → ship_check.
- Playwright pieces tested against a local static page served by `python3 -m http.server`.
- End to end with real spend: a small real web app built from a spec by
  `claude -p` children (interview with `--answers`, build milestones, persona,
  ship check).

## Exit codes (all scripts)

0 ok · 2 checks failed / spec invalid / NO-GO · 3 needs-human (baseline,
unresolved gap, unanswerable, cap reached) · 4 infra (a check could not
run; a required source blocked here) · 5 PIVOT (validation only) · 1 usage
error.
